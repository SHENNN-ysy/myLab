# MyBlog 测试工作流

> 本文档梳理项目当前的测试设施、完整的验证流程与新增功能时的测试要求。
> 最后更新：2026-08-13（对应死代码清理与注释补齐后的代码基线）

## 一、测试现状总览

项目采用"后端单元测试 + 架构规则测试 + 前端类型门禁 + 整栈冒烟"的组合，**没有集成测试、API 测试和 E2E 测试**。

| 层 | 设施 | 规模 | 运行条件 |
|---|---|---|---|
| 后端单元测试 | JUnit 5 + Mockito（`backend-java/src/test`，10 个文件） | 656 行 | 仅 JDK + Maven，**不需要 Docker/数据库/Redis** |
| 架构规则测试 | ArchUnit（`LayeredArchitectureTest`） | 61 行，6 个断言 | 同上 |
| 前端类型门禁 | `vue-tsc -b`（随 `npm run build` 强制执行） | 全量类型检查 | Node.js |
| 整栈冒烟 | `docker compose up -d --build` + 手工/接口验证 | — | Docker |
| CI | **无**（仓库无 `.github/workflows`） | — | — |

后端测试全部是纯单元测试：服务层用 Mockito mock 仓储/端口，不启动 Spring 容器、不连真实中间件（`pom.xml` 中引入了 Testcontainers 依赖，但目前没有任何测试使用它）。

## 二、各层详解

### 2.1 后端单元测试（`backend-java/src/test/java/com/myblog/`）

现有 10 个测试文件，按职责分四组：

**服务层（mock 依赖，验证用例逻辑）**
- `ContentModuleServiceImplTest`（199 行）——版本化内容域的核心用例：草稿保存、发布校验、状态流转
- `EngagementServiceTest`（106 行）——互动统计：降级路径、访客校验、趋势拼接
- `FileServiceImplTest`（101 行）——文件上传：白名单校验、OSS 端口 mock（"站内图片不需要 OSS"的降级语义就是在这里验证的）
- `SystemServiceTest`（43 行）——健康状态聚合

**契约与公共层**
- `ErrorCodeTest`、`ResultTest`、`CurrentUserTest`、`UserOutVOTest`——响应包络、错误码、身份模型的基础语义
- `GlobalExceptionHandlerTest`——异常→错误码的翻译边界（《错误码文档》第 5 节维护约定要求：新增错误码必须补充映射测试）

**架构规则（ArchUnit）**
- `LayeredArchitectureTest`（61 行）——把 `ARCHITECTURE.md` 的七条依赖规则落为可执行断言：应用核心不得依赖 infrastructure、application 不得依赖 controller/starter、common 不得依赖外层、controller 不得直达 infrastructure、starter 不得依赖 controller、应用服务包之间无循环依赖。**新增包/跨层调用前，先想清楚能不能过这道门。**

### 2.2 前端类型门禁（admin/ 与 myblog/）

两端均**没有单元测试框架**（无 Vitest/Jest）。唯一的自动化质量门是构建脚本里的类型检查：

```json
"build": "vue-tsc -b && vite build"
```

类型错误会直接阻断构建，这是前端目前唯一的回归防线。

### 2.3 整栈冒烟

```bash
docker compose up -d --build   # db / redis / api / web 四服务
```

起栈后可用以下方式验证：
- Swagger UI：`http://localhost:8000/swagger-ui.html`（仅本机直连 api 容器；nginx 已不对公网放行 `/swagger-ui`、`/v3/api-docs`）
- 健康检查：`GET /api/v1/health`
- 内容基线校验 SQL：`scripts/verify-content-baseline.sql`（数据库迁移后人工执行，验证内容数据完整性）

## 三、完整工作流（改完代码后按此执行）

### 第 1 步：后端测试

```powershell
# 标准命令（依赖已在默认本地仓库时）
mvn -f backend-java/pom.xml clean test

# 本机离线仓库写法（依赖缓存于 D:/MyBlog/.m2/repository）
mvn -s tmp/maven-settings.xml -f backend-java/pom.xml -o test

# 只跑指定测试（日常改动的快速回路）
mvn -s tmp/maven-settings.xml -f backend-java/pom.xml -o test -Dtest='LayeredArchitectureTest,ContentModuleServiceImplTest'
```

要求：全部通过。涉及跨层调用、新增包时，`LayeredArchitectureTest` 必须跑。

### 第 2 步：前端构建（两端都要）

```powershell
cd admin;  npm run build    # vue-tsc 类型检查 + vite 构建
cd myblog; npm run build
```

要求：类型检查无错误，构建成功。

### 第 3 步：整栈冒烟（涉及接口契约、数据库、部署的改动）

```powershell
docker compose up -d --build
# 验证：健康检查 200、Swagger 可访问、前台页面正常、后台可登录
```

以下改动**必须**走到这一步：
- 修改了 `db/migration/` 下的 SQL（注意：迁移脚本只在**空数据卷首次初始化**时自动执行，存量库需手工执行迁移 + 跑 `scripts/verify-content-baseline.sql`）
- 修改了公开接口的字段/契约（前台依赖全可选字段 + 兜底，契约破坏是**静默**的，必须人工核对前台展示）
- 修改了 Dockerfile、nginx.conf、docker-compose.yml

### 第 4 步：文档同步（本项目硬性约定）

- 新增/调整错误码 → 更新 `docs/错误码文档.md` + 补充异常映射测试（《错误码文档》第 5 节）
- 接口变更 → 更新 `docs/API接口文档.md` 并检查 `/v3/api-docs`
- 架构规则/包结构变更 → 更新 `backend-java/ARCHITECTURE.md` 与 `LayeredArchitectureTest`

## 四、新增功能时的测试要求

| 改动类型 | 必须补充 |
|---|---|
| 新应用服务/用例 | 对应 `XxxServiceImplTest`（Mockito mock 仓储与端口） |
| 新错误码 | `ErrorCode` 唯一性 + `GlobalExceptionHandlerTest` 映射用例 |
| 新包或新跨层依赖 | 检查/扩充 `LayeredArchitectureTest` |
| 内容模块结构变更 | 发布校验用例（双层校验：草稿宽松、发布严格） |
| 前端改动 | 至少保证 `vue-tsc` 通过；关键交互走第 3 步人工冒烟 |

## 五、已知缺口（诚实清单）

1. **无集成测试**：`JdbcContentReleaseRepository`（733 行 SQL 装配器）是整个系统最复杂、最易错的代码，却没有真实数据库测试。Testcontainers 依赖已在 `pom.xml` 中就位但未使用——补上它是当前投入产出比最高的测试改进。
2. **无 CI**：所有验证靠本地自觉执行，建议至少加一个跑 `mvn test` + 两端 `npm run build` 的流水线。
3. **前端零测试**：前台 8.4k 行组件（含手写图形算法）无任何回归保障；目前只能靠 `vue-tsc` + 肉眼。
4. **契约无机器校验**：前后端字段对齐靠人工，后端改字段前台会静默滑向兜底——建议引入 OpenAPI → TS 类型生成或契约测试。
5. **迁移无自动化验证**：存量库的迁移执行与校验（备份 → 手工 psql → verify SQL）是纯人工流程。
