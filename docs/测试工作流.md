# MyBlog 测试工作流

> 最后更新：2026-08-25

## 一、质量门

| 层级 | 工具 | 运行位置 |
|---|---|---|
| 后端单元测试 | JUnit 5 + Mockito | mvn verify |
| 后端集成测试 | Spring Boot + Testcontainers PostgreSQL/Redis | mvn verify |
| 架构约束 | ArchUnit | mvn verify |
| 静态质量 | Checkstyle + SpotBugs + JaCoCo | mvn verify |
| 前端质量 | ESLint + vue-tsc + Vite build | 两个前端目录 |
| 部署验证 | Compose healthcheck + API 冒烟 | CD / 本地 |

集成测试文件使用 *IT.java 命名，由 Maven Failsafe 在 integration-test 和 verify 阶段执行。CI 通过挂载 docker.sock 启动真实 PostgreSQL 与 Redis 容器。

## 二、本地验证

### 2.1 后端

在 backend-java 目录执行：

    mvn test
    mvn verify

- mvn test 适合快速单元测试；
- mvn verify 是提交前质量门，包含集成测试和全部静态检查；
- Testcontainers 测试要求本机 Docker 可用。

### 2.2 前端

分别在 myblog 和 admin 目录执行：

    npm ci
    npm run lint
    npm run build

admin 生产路径由 VITE_ADMIN_ROUTE 注入；默认使用 /admin。

### 2.3 整栈冒烟

根目录 Compose 是本地源码一键部署入口：

    docker compose up -d --build
    docker compose ps

验证：

- backend、frontend-web、frontend-admin、nginx 均为 healthy；
- GET /api/v1/health 返回成功；
- 前台页面可访问；
- 后台可登录；
- 数据库迁移后可运行 scripts/verify-content-baseline.sql。

## 三、CI 行为

所有分支：

1. 后端执行 mvn verify；
2. 两个前端并行执行 npm ci、lint、build；
3. 任一质量门失败则流水线失败。

仅 master：

1. stash 已验证的 JAR 和两个 dist；
2. Build Images 封装运行镜像，不重复测试；
3. Push Images 推送三个同 tag 镜像；
4. 归档 release.env。

CI 构建镜像不等于重新编译源码，部署内容就是前面质量门产生的构建产物。

## 四、CD 验证

CD 修改容器前必须完成：

1. Registry 容器健康检查；
2. Registry /v2/ API 检查；
3. 三个镜像 tag 与 digest 检查；
4. 三个镜像拉取；
5. admin 镜像与 deploy/.env 的 ADMIN_ROUTE 检查。

部署后轮询四个应用服务健康状态。失败时保留现场并输出日志，不更新当前成功版本状态文件。

## 五、改动要求

| 改动类型 | 最低验证 |
|---|---|
| 后端业务逻辑 | 对应单测 + mvn verify |
| 数据库、Redis、认证接口 | 新增或更新 Testcontainers 集成测试 |
| 新包或跨层依赖 | ArchUnit |
| 前端改动 | lint + build |
| Dockerfile、Compose、Nginx | 本地与生产 Compose config + 整栈冒烟 |
| CI/CD、Registry 脚本 | shell 语法、Compose config、Registry dry-run |

新增错误码同步更新错误码文档和异常映射测试；接口契约变化同步更新 API 文档。

## 六、当前缺口

- 前端尚无 Vitest/Jest 自动化测试；
- 前后端契约仍主要依赖人工同步；
- 浏览器端 E2E 测试尚未接入；
- Registry 清理首次上线必须人工 dry-run 验证保留集合。
