# 通用测试工作流

> 一份可以套用到任意项目的测试方法论。核心思想：测试不是"写用例"这一个动作，而是从策略、分层、设计、执行到治理的完整闭环。每一步都回答"做什么、怎么做、为什么"。

## 前言：为什么测试需要一个工作流

没有工作流时，测试最常见的死法有三种：

- **凭感觉写**：新功能顺手写两个用例，覆盖率看起来不错，但关键路径（异常、并发、边界）一个都没测到；
- **补票式写**：上线前集中补测试，写出来的用例只验证"代码做了什么"而不是"应该做什么"，重构一次全红；
- **门禁缺失**：测试写了但没人跑，本地靠自觉，合入靠运气，测试套件逐渐腐烂成没人敢碰的负资产。

工作流的目标是把测试从"个人习惯"变成"可重复执行的工程流程"：先定策略，再定分层，再设计用例，然后接入流水线持续执行，最后持续治理。

---

## 第 1 步：测试策略——先想清楚"什么值得测"

**做什么**：在写任何一行测试之前，先回答三个问题。

**具体动作**：

1. **风险盘点**：列出系统里"出错代价最高"的路径——资金、数据一致性、安全、核心业务流程。这些路径的测试优先级永远最高；
2. **边界划分**：明确哪些东西**不**测——第三方库内部行为、框架自身、纯转发无逻辑的代码、一次性脚本。给"不测"一个成文的理由，避免团队靠默契；
3. **质量门槛**：定出可验收的底线，例如"核心服务逻辑必须有单元测试""公开 API 必须有契约测试""合入必须全绿"。门槛写下来，才算存在。

**为什么这么做**：

- 测试是有成本的资产，追求"到处都有测试"必然导致重要的地方测得不够。风险驱动的优先级让有限的测试预算花在刀刃上；
- "不测什么"和"测什么"同等重要——边界不清的团队会在 getter、DTO、自动生成代码上浪费大量测试工时；
- 门槛不成文就不存在：口头约定的"要写测试"在 deadline 面前永远第一个被牺牲。

---

## 第 2 步：测试分层——选对每一层的武器

**做什么**：按测试金字塔确定项目使用哪几层、各层职责与大致配比。

**各层定位**：

| 层 | 测什么 | 特征 | 典型工具 |
|---|---|---|---|
| 单元测试 | 单个函数/类的逻辑、分支、异常 | 快（毫秒级）、隔离、可定位 | JUnit / Vitest / pytest |
| 集成测试 | 模块与真实依赖的协作（DB、缓存、消息队列） | 中速、需要环境 | Testcontainers / 内存库 / docker-compose |
| 契约测试 | 服务间/前后端接口约定 | 防"接口悄悄变了" | OpenAPI 校验 / Pact / 类型生成 |
| E2E 测试 | 关键用户旅程全链路 | 慢、脆弱、昂贵 | Playwright / Cypress |
| 静态门禁 | 类型、Lint、格式 | 零运行时成本 | tsc / ESLint / ArchUnit / Checkstyle |

**具体动作**：

1. 配比遵循金字塔：大量单元测试打底，少量集成测试验证协作，极少 E2E 只覆盖"钱级"用户旅程。倒金字塔（一堆 E2E）是最常见的反模式——慢、脆、定位难；
2. **静态门禁优先于动态测试**：类型检查、Lint、架构规则测试（如 ArchUnit 强制分层依赖）能以接近零的成本挡住整类错误，应作为第一道门；
3. 每一层明确"这一层的失败意味着什么"：单元测试红 = 逻辑错；集成测试红 = 协作/环境错；E2E 红 = 可能真的全断了，也可能只是测试脆。

**为什么这么做**：

- 不同层的缺陷发现成本差一个数量级：单元测试分钟级定位，E2E 可能要翻半小时日志。能在下层抓到的问题绝不上移；
- 契约层是微服务/前后端分离架构里最容易被省掉、又最疼的一层——接口双方各自测试全绿、联调全挂，缺的就是它。

---

## 第 3 步：用例设计——测"应该做什么"，不是"做了什么"

**做什么**：针对被测对象系统地推导用例，而不是照着代码分支抄一遍。

**具体动作**：

1. **从行为出发**：先写"输入 → 期望输出/副作用"的清单，覆盖正常路径、边界值（空、零、最大值、重复、并发）、异常路径（非法输入、依赖故障、超时）。等价类划分 + 边界值分析是最实用的两个手法；
2. **结构遵循 AAA**：Arrange（准备数据）→ Act（执行一次调用）→ Assert（断言结果）。一个用例只验证一件事，用例名本身就是规格说明（`发布时旧版本应归档为新状态`）；
3. **好测试的 FIRST 标准**：Fast（快）、Independent（用例间无依赖、无顺序要求）、Repeatable（任何环境重复结果一致）、Self-validating（要么过要么挂，不需要人工看输出）、Timely（随代码同步维护）；
4. **断言行为而非实现**：不要断言"内部调用了某私有方法三次"，要断言对外可观察的结果。绑死实现的测试会让每次重构都变成改测试。

**为什么这么做**：

- 照着代码抄出来的测试是"变化检测器"不是"回归保护网"——代码怎么改它都说对，唯一的用处是制造安全感；
- 异常路径和边界值是真实 bug 的富矿，也是凭感觉写测试时最先被跳过的地方；
- 用例名即文档：半年后接手的人（或 AI）读测试名就能理解系统的行为规格。

---

## 第 4 步：融入开发流程——什么改动跑到哪一层

**做什么**：把测试执行嵌入日常开发节奏，明确"改什么代码，必须跑什么测试"。

**具体动作**：

1. **本地快速回路**：改动后先跑相关模块的单元测试（秒级反馈），提交前跑全量单元 + 静态门禁；
2. **改动-测试对照表**（示例，按项目裁剪）：

| 改动类型 | 最低要求 |
|---|---|
| 业务逻辑 | 新增/更新单元测试，相关模块全绿 |
| 接口契约 | 更新契约定义 + 契约测试，通知消费方 |
| 数据库结构 | 迁移脚本可空库重放 + 数据迁移有回滚方案 |
| 架构/包结构 | 架构规则测试同步更新 |
| 文档声明的行为 | 文档与测试至少有一个是对的，且同步改 |

3. **新功能与测试同 PR**：功能代码和它的测试是同一个交付物，不接受"测试下个迭代补"；
4. **bug 修复先写复现用例**：先写一个能复现 bug 的红测试，再修代码让它变绿——这个用例从此成为该 bug 的终身看守。

**为什么这么做**：

- 测试滞后于代码就会永远滞后：没有 PR 级门禁，"补测试"永远排不进排期；
- bug 复现用例把"这次踩坑"变成"永久免疫"，是测试资产复利最高的来源。

---

## 第 5 步：流水线门禁——让测试不靠自觉

**做什么**：搭建 CI，把"全绿才能合入"变成机器强制的规则。

**具体动作**：

1. **分层流水线**：

```text
PR 触发
  → 第一级（分钟级）：静态检查 + 编译 + 单元测试      ← 卡 90% 的问题
  → 第二级（十级分钟）：集成测试 + 契约测试           ← 合并前必须通过
  → 第三级（按需/夜间）：E2E + 性能基线               ← 不阻塞 PR，阻塞发布
```

2. **失败纪律**：流水线红了要么立刻修、要么立刻回滚，**不允许跳过测试合入**（skip 一次就会有第一百次）；
3. **环境一致性**：测试环境用容器化固定（Testcontainers / docker-compose），消灭"我机器上是好的"。

**为什么这么做**：

- 靠自觉的测试等于没有测试。门禁的价值不在拦住高手，而在保护所有人（包括 AI 协作者）不在疲惫时犯错；
- 分级是成本和保障的平衡：把所有测试塞进 PR 门禁会让流水线慢到大家想办法绕开它。

---

## 第 6 步：度量与治理——防止测试资产腐烂

**做什么**：持续监控测试套件的健康度，定期清理。

**具体动作**：

1. **覆盖率当参考不当目标**：行覆盖率 80% 但全是"跑过就算"的用例毫无意义。看覆盖率找**未覆盖的区域**，不看数字高低；有条件的可以上变异测试（mutation testing）检验断言的真实强度；
2. **脆弱测试（flaky）零容忍**：随机失败的测试要么修要么删——留着它，团队就会养成"红了重跑"的习惯，测试的可信度随之归零；
3. **定期审计**：删除随功能下线的测试、合并重复用例、把慢测试移出快速回路。测试代码和产品代码一样需要重构。

**为什么这么做**：

- 测试是资产也是负债：每个用例都有维护成本，失去信任的测试套件比没有测试更糟——它提供虚假的安全感。

---

## 验收清单（可复用）

新项目落地或老项目补课时，逐项检查：

- [ ] 有成文的测试策略：风险优先级、"不测什么"的清单、质量门槛
- [ ] 分层明确：单元/集成/契约/E2E 各层职责与配比符合金字塔
- [ ] 静态门禁（类型/Lint/架构规则）作为第一道门接入
- [ ] 用例设计从行为出发，覆盖正常/边界/异常三类路径
- [ ] 用例满足 FIRST，断言行为而非实现
- [ ] 有"改动类型 → 必须跑的测试"对照表
- [ ] 功能与测试同 PR；bug 修复先写复现用例
- [ ] CI 分级流水线，全绿才能合入，无跳过通道
- [ ] 测试环境容器化，无"我机器上是好的"
- [ ] 覆盖率用于发现盲区而非追求数字；脆弱测试零容忍

## 总结

通用测试工作流可以归纳为：

```text
定策略（测什么/不测什么）
  → 分层（每层的职责与配比）
  → 设计用例（行为驱动，三类路径）
  → 融入开发（改动-测试对照，同 PR 交付）
  → 流水线门禁（分级执行，全绿合入）
  → 度量治理（防腐烂，保持可信）
```

好的测试体系不追求用例数量，而是追求三件事：**缺陷在下层被抓到、门禁不依赖自觉、套件十年后依然可信**。
