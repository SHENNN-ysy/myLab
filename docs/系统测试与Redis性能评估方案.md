# MyBlog 系统测试与 Redis 性能评估方案

> 第一次执行系统测试时，建议先使用[基础版方案](系统测试与Redis性能评估方案-基础版.md)。本文档作为完成基础测试后的进阶参考。

## 1. 方案目标

本方案用于回答四个问题：

1. 系统的核心业务在正常、并发和故障条件下是否正确；
2. 当前单实例部署在既定资源下能够稳定承载多少流量，瓶颈首先出现在哪里；
3. Redis 对延迟、吞吐、PostgreSQL 负载和整体资源效率分别带来了多少改善；
4. 在不同流量和故障压力下，应该采用预热、限流、扩容、降级还是快速失败，才能保持系统稳定且高效。

最终交付物应包含：

- 功能、兼容性、安全性和故障恢复测试报告；
- 容量曲线，以及各接口的 p50、p95、p99 延迟和错误率；
- Redis 开启/关闭的可复现实验结果与统计结论；
- PostgreSQL、Redis、JVM、Tomcat、连接池和容器资源的瓶颈证据；
- 正常运行、告警、扩容和过载保护的建议阈值；
- 发现的问题、修复优先级及修复后的回归结果。

## 2. 测试边界：什么才是“使用和不使用 Redis”

项目中的 Redis 同时承担公开内容缓存、管理会话、限流、互动实时计数、访客去重、已发布文章索引和 Stream 异步通知。直接停止 Redis 会同时改变多项业务语义，不能把它简单解释成“无缓存版本”。

| 对照对象 | 可否做等价 A/B | 正确对照方式 | Redis 不可用时的实际行为 |
|---|---:|---|---|
| 公开内容缓存 | 可以 | A 组 `CONTENT_CACHE_ENABLED=true`，B 组 `false`；两组 Redis 均保持健康 | 读取回源 PostgreSQL，属于故障降级 |
| 互动统计读取 | 不完全等价 | 比较 Redis 实时值与 PostgreSQL 最近快照的延迟、数据新鲜度 | 返回 PostgreSQL 快照，可能滞后 |
| 互动统计写入 | 不可以 | 如需比较，必须另做一个具有相同去重、幂等和事务语义的同步 PG 测试实现 | 浏览、点赞、取消点赞失败，不伪造成功 |
| 管理会话 | 不可以 | 测 Redis 正常时的性能及故障时的安全行为 | 登录和受保护接口返回 503 |
| Redis 限流 | 不可以直接等价 | 单独验证阈值、误杀、故障放行及 Nginx 第二道防线 | 应用层限流 fail-open |

因此，本方案中的正式 Redis A/B 结论只针对以下三个公开内容读取接口：

- `GET /api/v1/public/content`
- `GET /api/v1/public/content/mylab`
- `GET /api/v1/public/mylab/{postKey}`

Redis 整体停机则归入故障注入和恢复测试，报告中不得将其数据混入公开缓存 A/B 结果。

## 3. 当前系统基线

测试报告必须记录实际运行配置，避免结果脱离环境后失去意义。当前仓库默认基线如下：

| 层级 | 当前基线 |
|---|---|
| 部署形态 | 单后端实例、单 PostgreSQL、单 Redis |
| 后端容器 | 内存 1 GiB；JVM `-Xms256m -Xmx768m`，G1 GC |
| Tomcat | 最大线程 50，最小空闲线程 5 |
| HikariCP | 未配置最大连接数，使用默认 10；连接超时 10 秒 |
| PostgreSQL | `max_connections=30`，`shared_buffers=256MB`，容器内存 768 MiB |
| Redis | 最大内存 128 MiB，`noeviction`，AOF `everysec`，容器内存 160 MiB |
| 公开内容缓存 | TTL 6 小时，重建锁 5 秒，等待窗口 1 秒 |
| 互动 Stream | 批量 500，阻塞 2 秒，轮询 1 秒，Pending 接管 30 秒，单活租约 30 秒，保留 72 小时 |
| 匿名访客状态 | 24 小时滑动过期 |
| 应用限流 | 普通接口 60 次/分钟/IP，登录 5 次/分钟/IP |
| Nginx 限流 | API 10 次/秒/IP、burst 20；登录 3 次/分钟/IP、burst 5；API 并发连接 10/IP |

开始每轮测试前，至少保存以下元数据：Git SHA、镜像 tag、测试数据版本、环境变量、容器资源限制、主机规格、JDK/PG/Redis 版本、网络拓扑、测试工具版本、测试时间和是否启用 ARMS。

故障演练前还要确认 Lettuce/Redis 客户端实际生效的连接与命令超时。当前主配置没有显式声明 Redis 命令超时，“连接立即拒绝”和“连接建立但命令长期变慢”的影响会完全不同；若不记录运行时超时，慢 Redis 的测试结果无法解释。

## 4. 测试环境与可重复性要求

### 4.1 环境隔离

- 使用独立的类生产环境，禁止在正式库上执行容量、破坏性或故障注入测试；
- 压测机与被测机分离，确认压测机 CPU、网络和端口没有先成为瓶颈；
- A/B 两组使用同一代码、数据、镜像、资源配额、日志级别、TLS/Gzip 配置和 OSS 依赖；唯一变量是 `CONTENT_CACHE_ENABLED`；
- A/B 不在同一台机器上同时运行，避免两组争抢 CPU、磁盘和网络；按 A-B-B-A 或随机顺序重复执行；
- 每次重启后先进行至少 5 分钟 JVM/JIT 预热，再采集稳定阶段数据；
- 每个正式场景至少重复 3 次，建议 5 次，报告中给出中位数及 95% 置信区间；
- 外部 OSS 应使用稳定的测试 Bucket 或等价桩服务，避免公网抖动污染后端结论。

### 4.2 两条压测链路

容量测试和真实入口测试必须分开：

| 测试平面 | 入口 | 配置 | 目的 |
|---|---|---|---|
| 后端容量平面 | 同 Docker 网络、SSH 隧道或测试专用私网端口访问后端 | 通过 Compose override 显式透传并提高 `RATE_LIMIT_*`，或使用可控的多来源地址 | 测后端、PG、Redis 的真实容量和瓶颈 |
| 端到端平面 | HTTPS → Nginx → 后端 | 保持生产限流、TLS、代理和连接设置 | 验证真实访问链路、429、代理开销和保护效果 |

如果使用单个来源 IP 直接压 Nginx，当前配置会先在约 10 req/s 触发 Nginx 限流；如果绕过 Nginx却保留应用默认值，则会在 60 次/分钟/IP 触发应用限流。此时只能得出限流规则生效，不能得出系统容量只有这些数值。

当前 Compose 只把后端 `8000` 端口绑定到宿主机 `127.0.0.1`，独立压测机不能直接访问。容量平面不得为了省事把端口裸露到公网；应选择同一私有 Docker 网络的 k6、SSH 隧道，或仅允许压测机地址访问的测试专用私网绑定。

### 4.3 数据集

准备三个可重置的数据快照：

| 数据集 | 规模 | 用途 |
|---|---|---|
| D0 | 脱敏后的当前数据量 | 功能回归和当前容量基线 |
| D1 | 预计 6～12 个月数据量的 5 倍 | 常规容量与索引稳定性 |
| D2 | D1 的 4 倍，即当前约 20 倍 | 极限、分页、历史版本和高基数测试 |

MyLab 正文至少包含约 5 KiB、100 KiB 和接近 500,000 字符上限三档；准备热门、普通、冷门以及不存在的 `postKey`。互动数据还应覆盖大量匿名访客、单一热点文章、大量长尾文章、120 天每日统计和 72 小时 Stream 消息量。

数据库快照、Redis 初始状态和测试账号必须可一键恢复。缓存清理只能删除本次实验明确涉及的 key，禁止在共享环境执行 `FLUSHDB`。

## 5. 可观测性准备

没有服务端指标时，客户端延迟只能说明“慢了”，无法说明“为什么慢”。当前 Actuator 仅暴露 `health,info`，正式压测前应先补齐测试环境的观测面。

### 5.1 建议新增或开放的指标

- 在仅测试网络可访问的端口暴露 Micrometer/Prometheus 指标，或使用 ARMS 采集 HTTP、JVM、Tomcat、Hikari 和 SQL 指标；生产公网不得直接暴露；
- 为公开内容缓存增加：
  - `content.cache.requests{unit,outcome=hit|miss|bypass|error}`；
  - `content.cache.rebuild.duration`；
  - `content.cache.lock{unit,outcome=acquired|contended|timeout}`；
  - 数据库回源次数和回源耗时；
- 保留并采集现有互动 Stream 指标：处理消息数、消费失败数、批次耗时、最近成功时间、Stream 长度和 Pending 数；
- 增加“最老未落库事件年龄”或“事件产生到 PostgreSQL 提交”的延迟指标，避免仅看 Pending 数漏掉少量长期卡住的消息；
- PostgreSQL 测试环境启用 `pg_stat_statements`，采集调用数、总耗时、平均耗时、共享块命中和临时文件；
- Redis 采集 `INFO`、`LATENCY`、内存、命令吞吐、连接数、拒绝连接、AOF 重写和写入失败；
- 使用容器或主机监控采集 CPU、内存、磁盘 IOPS、磁盘等待、网络吞吐和容器重启次数。

### 5.2 健康检查专项

当前 `/api/v1/health` 的总体状态主要由数据库决定：Redis 故障时仍可能显示健康，数据库异常时该接口也可能继续返回 HTTP 200。容器健康检查只判断 HTTP 200，存在“业务已降级但编排仍判定健康”的风险。

测试时应同时断言：

- `/api/v1/health` 的 HTTP 状态、JSON 中数据库状态和 Redis 状态；
- `/actuator/health` 的总体状态以及 readiness/liveness；
- Docker/编排层看到的容器健康状态；
- 告警是否在约定时间内触发和恢复。

该项的结果应单独形成“健康检查与就绪探针缺口”，不能只以 HTTP 200 判定测试通过。

## 6. 关键指标与第一轮验收门槛

以下数值是用于第一轮摸底的工程门槛，不是永久 SLO。第一轮得到稳定容量和真实分布后，应结合服务器规格、业务量和成本重新校准。

### 6.1 客户端与业务指标

| 指标 | 第一轮门槛 |
|---|---:|
| 公开内容热缓存读取 | p95 ≤ 100 ms，p99 ≤ 250 ms |
| 公开内容冷缓存或直查 PG | p95 ≤ 400 ms，p99 ≤ 1 s |
| 互动读取/写入 | p95 ≤ 150 ms，p99 ≤ 400 ms |
| 常规后台读取和已登录鉴权 | p95 ≤ 200 ms，p99 ≤ 500 ms |
| 发布/下线事务 | p95 ≤ 800 ms，p99 ≤ 2 s |
| BCrypt 登录 | p95 ≤ 800 ms，p99 ≤ 1.5 s；单独测，不混入普通 API 容量 |
| 非预期 5xx | ≤ 0.1% |
| 客户端网络超时 | 0 |
| 功能正确性、越权、计数负数、已发布旧内容回写 | 0 次 |
| 混合读流量缓存命中率 | ≥ 95%；首页和列表稳定后目标接近 99% |
| 开启缓存后的相关 PG 查询下降 | ≥ 90% |
| Stream 落库延迟 | p95 ≤ 5 s，p99 ≤ 15 s |

所有延迟必须同时报告 p50、p90、p95、p99 和最大值；吞吐应拆分 offered、accepted、achieved RPS 和压测工具 dropped iterations；错误必须拆分为 400/401/403/404/409/429/503/其他 5xx/客户端超时，不能只给一个总错误率。

### 6.2 服务端资源指标

| 层级 | 建议稳定区/门槛 |
|---|---|
| 后端 CPU | 稳态均值 < 65%，短时峰值 < 80%；不得持续 90% |
| JVM | 无 OOM、无 Full GC 风暴；GC 总耗时 < 2%，p99 pause < 100 ms；GC 后堆占用 < 70% |
| Tomcat | busy threads 不应持续超过 35/50；队列和拒绝数不持续增长 |
| HikariCP | active 通常不超过 7/10，pending 稳态为 0，获取连接不得接近 10 秒超时 |
| PostgreSQL | 连接数 < 30 的 70%，死锁 0；慢 SQL、锁等待和临时文件无持续增长 |
| Redis | 使用内存 < 128 MiB 的 70%，本机命令 p99 < 5 ms；拒绝写入、OOM、意外驱逐均为 0 |
| Stream Consumer | Pending 不单调增长；停止生产后能在目标时间内清空；单批 p99 < 10 s，严禁接近 30 秒租约 |
| 容器 | 无 OOMKilled、无意外重启，磁盘可用空间始终 > 15% |

## 7. 系统功能与一致性测试矩阵

### 7.1 公开内容缓存

| 编号 | 场景 | 核心断言 |
|---|---|---|
| CACHE-F01 | 首页、MyLab 列表、详情首次读取 | 未命中时回源，响应正确，缓存成功写入 |
| CACHE-F02 | 热缓存重复读取 | 内容一致，命中率上升，PG 调用显著下降 |
| CACHE-F03 | 不存在/未发布详情 | HTTP 返回 404，同时内部形成负缓存，重复请求不持续打 PG |
| CACHE-F04 | Redis 读写异常 | 公开读取回源 PG；响应不因缓存故障直接失败 |
| CACHE-F05 | 缓存载荷损坏或结构不兼容 | 不返回错误结构；记录异常并回源或清理 |
| CACHE-F06 | 发布、下线、标签变化 | 仅在数据库提交后失效正确的首页、列表和详情缓存 |
| CACHE-F07 | 发布事务回滚 | 缓存不被无故清除，公开内容不变化 |
| CACHE-F08 | 旧请求重建与发布并发 | 发布成功后旧值不能重新覆盖新内容 |
| CACHE-F09 | 多个详情同时冷加载 | 观察当前详情共用逻辑锁造成的串行等待和超时回源 |
| CACHE-F10 | Redis 故障期间发布/下线，随后恢复 | 验证失效或已发布索引重建失败且无重试时，AOF 旧状态的陈旧窗口和最终收敛 |

缓存响应还要校验 OSS object key 与临时资源 URL 的边界：缓存中不应固化过期签名 URL，每次命中后生成的资源 URL 都应在当前时间有效。

负缓存需要单独进行内存测试。合法格式但不存在的 `postKey` 会成为共用详情 Hash 的空 field，而写入任一新 field 都会刷新整个 Hash 的 TTL。持续请求随机合法 key 时，应记录正/负 field 数、Hash 内存、TTL 是否长期不归零，以及 Redis 128 MiB `noeviction` 后对会话、互动和限流写入的连带影响。

### 7.2 会话和权限

- 登录成功后只向客户端返回原始 Token，Redis 中只存在摘要；
- 会话在有效请求后按 8 小时空闲窗口滑动续期；
- 退出登录幂等，退出后 Token 立即失效；
- 修改密码、用户名、角色、启用状态及删除用户后，该用户全部会话立即吊销；
- 普通管理员、超级管理员和未登录用户的接口权限边界正确；
- Redis 异常时登录和受保护接口返回 503，而不是误报 401 或 fail-open；
- 并发登录与敏感账号修改时，PostgreSQL 用户行锁没有漏发有效会话；
- Token、密码、HMAC 密钥和签名 URL 不出现在应用日志、访问日志和错误响应中。

### 7.3 版本化内容和数据库事务

- 每个模块至多一个 DRAFT 和一个 PUBLISHED；发布生成不可变历史版本；
- `expected_updated_at` 在并发保存草稿时正确阻止覆盖，冲突返回 409；
- 发布、下线、恢复、归档、软删除和标签变更满足数据库约束；
- 历史恢复在目标记录上原地转为草稿，原草稿归档，不额外生成错误版本；
- 事务中任一步故障时，主表、模块明细、卡片、标签关联、资源引用和版本状态整体回滚；
- `AFTER_COMMIT` 事件只在事务提交后执行；回滚时不得触发缓存失效；
- MyLab 列表排序、项目展示位次、正文复制和历史数量与业务约定一致；
- 并发发布、发布与下线、删除与文件引用检查不存在死锁和脏状态。

### 7.4 UV/PV/点赞与异步落库

| 场景 | 核心断言 |
|---|---|
| 新访客首次访问 | visit、页面 view、站点和每日指标按口径增加 |
| 相同 Cookie 重复浏览 | 24 小时窗口内不重复累计对应页面浏览，但身份 TTL 滑动续期 |
| 多个虚拟用户 | 每个 VU 的独立 Cookie 只在首次互动产生首次写，后续请求进入去重路径；两类结果分开统计 |
| 首次点赞、重复点赞、取消点赞 | Lua 原子去重；重复点赞不加一；取消后不为负数 |
| 详情首次互动 | 必要时补记详情浏览，保证口径一致 |
| 并发点赞/取消 | 文章、全站、每日数据满足定义，Redis 中无负值或丢失更新 |
| Stream 重复投递 | Consumer 按 Redis 最新绝对值覆盖 PG，重放不重复累加 |
| Consumer 中断 | Pending/Stream 可积压；恢复后接管并收敛到 Redis 当前绝对值 |
| 畸形消息 | 进入死信 Stream，合法消息不被连带丢弃 |
| PG 提交失败 | 不 XACK；数据库恢复后可重试并最终一致 |
| 应用重启 | 超过 claim idle 后接管 Pending，未确认消息不被提前裁剪 |
| Redis 永久丢失 | 只能恢复 PG 最近快照；明确记录实时尾部和访客去重状态的数据损失窗口 |

Stream 安全裁剪还要覆盖消费组投递位置、最老 Pending 和保留期的组合，确认未确认消息不会只因超过名义保留时间而被提前删除。

### 7.5 文件、前端和安全

- 文件上传类型、大小、空文件、恶意扩展名、预签名 URL、引用检查和删除行为；
- 博客前台首页、MyLab 列表、详情、点赞及资源展示的浏览器 E2E；
- 后台登录、草稿编辑、并发冲突提示、发布、下线、版本恢复、用户管理的浏览器 E2E；
- 响应式布局、主流浏览器、慢网、刷新和路由直达；
- CORS、CSRF 设计边界、越权、路径/参数注入、超大 JSON、上传限制和错误信息泄露；
- Nginx 与应用双层限流阈值、边界值、突发量、不同来源及 Redis 故障时的 fail-open 行为。

建议保留现有 `mvn verify` 和前端 lint/build 作为准入门槛，并用 Playwright 补浏览器主流程；接口与负载使用 k6，安全基线可使用 OWASP ZAP，但任何主动攻击扫描只能在隔离环境进行。

### 7.6 部署、迁移与备份恢复

- 全新空库应能由 Flyway 完整初始化；已有库接管基线后再次启动应保持幂等；
- 使用生产镜像从旧版本升级到当前版本，验证迁移前后内容版本、用户、文件引用和统计快照；
- 验证 PostgreSQL 晚于后端启动时的失败、重启自愈和告警行为；
- 验证生产 Nginx 的 HTTPS 跳转、`ADMIN_ROUTE`、API 反向代理、请求体大小和静态资源路径；
- 实际执行 PostgreSQL 备份恢复、Redis AOF 恢复和镜像回滚演练，并核对 RPO/RTO；
- 回滚镜像前检查数据库迁移的向后兼容性，不能把“容器成功启动”当作业务回滚成功。

## 8. 流量模型

### 8.1 公开访客混合流量

第一轮使用以下请求比例，随后用生产访问日志校准：

| 请求 | 比例 |
|---|---:|
| 首页聚合 `GET /public/content` | 35% |
| MyLab 列表 | 20% |
| MyLab 详情 | 20% |
| 互动计数读取 | 10% |
| 页面浏览写入 | 12% |
| 点赞/取消点赞 | 3% |

至少运行四种数据分布：

1. 热点：80% 或 90% 的详情请求集中到一个 `postKey`；
2. 典型：20% 的内容承载 80% 的详情请求；
3. 均匀：文章被近似平均访问；
4. 长尾与穿透：大量不同或不存在的 `postKey`。

浏览去重至少要有三套身份脚本：每次迭代生成新身份，用于持续制造真实首次写入；每个 VU 固定独立 Cookie，用于“首轮写入、后续去重”的回访模型；多个 VU 明确复用同一 Cookie，用于并发幂等测试。不能把“每个 VU 一个 Cookie”误当作持续写入，因为每个 VU 首次迭代后就进入去重路径。点赞与取消点赞必须按每个身份维护状态机，否则大量请求只是幂等 no-op。

生产默认 Cookie 带 `Secure`，直连后端 HTTP 时 k6 可能不会回送该 Cookie。互动容量测试应优先走 HTTPS；若确需直连 HTTP，只能在隔离环境将 `VISITOR_COOKIE_SECURE=false`，并在所有对照组保持一致，同时显式检查 Cookie jar 中的值和 `Max-Age`。

### 8.2 后台与登录流量

后台发布、版本操作和用户管理应单独建模，不与公开 API 的容量数字混为一谈。登录因 BCrypt 成本较高，也应独立压测：测试合法登录、错误密码、同一 IP 限流、多 IP 攻击和数据库行锁竞争。

## 9. 压测阶段与容量判定

负载测试优先采用开放模型（如 k6 `constant-arrival-rate`），按目标到达率持续发请求，避免闭环虚拟用户因服务变慢而自动降低请求量，从而掩盖过载。

### 9.1 阶梯压测

1. 冒烟：1～5 RPS，确认脚本、数据、Cookie、断言和监控正确；
2. 阶梯：5 → 10 → 20 → 40 → 80 → 160 → 320 RPS；
3. 每档约 3 分钟爬升、10 分钟稳定、3 分钟冷却；
4. 首次越过 SLO 或资源门槛后停止翻倍，在最后成功档与失败档之间按约 10% 步长细化；
5. 在候选容量上持续 30 分钟仍满足全部 SLO，才记为可持续容量，而非瞬时峰值。

分别得到以下容量：

- `C_warm`：公开内容缓存开启且已预热；
- `C_off`：只关闭公开内容缓存，Redis 其他职责仍正常；
- `C_cold`：缓存开启但关键内容刚失效；
- `C_write`：互动写入与 Stream 消费稳定容量；
- `C_mix`：真实比例混合流量的稳定容量。

### 9.2 峰值和长稳

- 突发测试：从 `0.3 × C_mix` 在数秒内提升至 `1.5 ×` 和 `2 × C_mix`，维持 1～3 分钟，再降回基线；观察拒绝、排队、恢复和积压清理；
- 浸泡测试：以 `0.6～0.7 × C_mix` 连续运行 6～8 小时，观察堆、连接、Redis 内存、Stream 和句柄是否爬升；
- 24 小时口径验证：在预生产环境运行 24～30 小时，覆盖访客身份 24 小时 TTL，验证去重过期、每日切换和 Redis 内存是否可持续；
- 发布期测试：在 `0.5 × C_mix` 公开流量下执行发布、下线和标签修改，记录缓存失效、重建和新内容全量可见时间。

## 10. Redis 公开内容缓存 A/B 实验

### 10.1 实验组

| 组别 | `CONTENT_CACHE_ENABLED` | 缓存状态 | 用途 |
|---|---:|---|---|
| A1 | `true` | 预热完成 | 衡量热缓存收益 |
| A2 | `true` | 指定 key 冷启动 | 衡量首次回源和重建锁 |
| B | `false` | 不适用，Redis 仍健康 | 等语义 PostgreSQL 直查基线 |
| N | 任意 | 访问未缓存的公开模块接口 | 负对照，排查环境漂移 |
| F | `true` | Redis 延迟/中断 | 故障降级，不计入 A/B 性能收益 |

A1 与 B 的稳态比较都应先预热 JVM、连接池和 PostgreSQL buffer；切换开关需要重启应用时，两组执行相同的重启和预热流程。A2 只让 Redis 内容缓存为空，不得把 JVM 冷启动或 PG 冷盘读取混入同一结果。

冷启动只删除明确的三个内容缓存 key：

```text
mylab:blog:content:v3:all
mylab:blog:content:v1:mylab:summary
mylab:blog:content:v1:mylab:details
```

实际执行前必须从当前代码再次确认 key 版本，避免误删其他业务数据。

### 10.2 单接口实验

对首页、列表和详情分别执行：

1. 单请求冷加载，建立数据库回源基线；
2. 热缓存 1、10、50、100、200 并发；
3. 缓存关闭后的同等并发；
4. 同一热门详情并发冷加载，观察锁是否把 PG 回源压缩到约一次；
5. 50～200 个不同详情同时冷加载，观察当前共用详情逻辑锁带来的等待和超时回源；
6. 大量不存在的 `postKey`，验证负缓存能否阻止穿透；
7. TTL 同时到期、发布后失效和应用启动后的集中冷加载。

对回源人为增加约 0.2、0.8、1.2、3、4.5、5.5、6、8 秒延迟，重点观察两个设计边界：

- 超过 1 秒等待窗口后，未获得缓存的请求开始直接回源，但不写缓存；
- 超过 5 秒锁租约后，锁可能在重建中途失效并允许第二个请求重建。

故障注入只能在隔离环境通过 Toxiproxy、`tc netem` 或数据库测试钩子实施，不允许修改生产网络。

### 10.3 收益计算

```text
p95 延迟改善率 = 1 - p95_on / p95_off
稳定容量提升率 = C_warm / C_off - 1
PG 卸载率       = 1 - pg_queries_on / pg_queries_off
故障容量损失率 = 1 - C_fault / C_normal
资源效率        = achieved_rps / (backend_cpu + pg_cpu + redis_cpu)
```

结论不能只写“Redis 快了多少”。缓存收益成立需要同时满足：

- 延迟或稳定容量有显著改善；
- PostgreSQL 查询、CPU、I/O 或连接等待明显下降；
- 加上 Redis 自身开销后，整体资源效率仍提高；
- 响应内容、发布可见性和故障行为保持正确。

## 11. 互动统计专项性能测试

### 11.1 原子写路径

- 同一访客、同一文章高并发重复浏览，验证 Lua 去重成本和计数不重复；
- 大量新访客访问同一热门文章，验证单 key 热点、Redis 单线程延迟和 Stream 生产速度；
- 大量访客访问大量文章，验证高基数 key 数、内存增长和 AOF 写入压力；
- 点赞与取消点赞 1:1、9:1 和突发切换，验证计数不为负且响应延迟稳定；
- 将生产速率逐步提高到消费速率以上，绘制 Stream 长度、Pending、最老消息年龄和 PG 落库延迟曲线。

### 11.2 Consumer 与数据库

- 在 batch size 500 下测每批回读 Redis、去重和 PG upsert 耗时；
- 暂停 Consumer 30 秒、2 分钟和 10 分钟，恢复后测积压清空速率和最长恢复时间；
- 注入 PG 短暂失败，确认合法消息未提前 XACK；
- 重复投递、应用重启和 Pending 接管后，Redis 与 PG 聚合值最终完全一致；
- 验证单活租约：任何批次不得接近 30 秒。当前消费者由单租约维持单活，简单增加后端实例不会线性提高消费能力。

如果要回答“Lua + Stream 比同步 PostgreSQL 写快多少”，必须实现一个仅用于测试的同步 PG 版本，并具备与当前路径相同的访客去重、事务、幂等、内容状态校验和错误语义；否则对比结果无效。

## 12. 限流、过载与安全压力测试

### 12.1 限流边界

- 应用普通接口按每分钟 59、60、61 次及突发请求验证；
- 登录接口按 4、5、6 次/分钟验证，区分正确和错误密码；
- Nginx API 按低于、等于和高于 10 req/s，以及 burst 20 验证；
- 单 IP 与多 IP、短连接与 keep-alive、并发连接 9/10/11 分别验证；
- 确认 429 有明确且可观察的来源，不能与容量不足造成的 5xx 混在一起；
- Redis 故障时验证应用限流 fail-open，同时确认 Nginx/WAF 仍能形成第二道防线。

### 12.2 防滥用场景

对无效 `postKey`、超长参数、超大正文、批量不存在的资源、错误 Token、暴力登录、重复点赞和文件上传分别施压。目标不是追求高吞吐，而是证明异常流量不会耗尽 Tomcat 线程、Hikari 连接、Redis 内存或 PostgreSQL CPU。

## 13. 故障注入与恢复测试

| 故障 | 注入方式 | 预期行为 | 必须记录 |
|---|---|---|---|
| Redis 延迟 20/100/500 ms | 网络代理注入 | 延迟上升可观测；缓存/会话/互动按各自语义处理 | 首次超 SLO、超时和恢复点 |
| Redis 中断 30/120 秒 | 隔离网络或暂停容器 | 公开内容回源 PG；互动读取回 PG 快照；互动写和会话返回 503；应用限流 fail-open | 错误比例、PG 放大、恢复时间 |
| Redis 中断期间发布/下线 | 预热后中断 Redis，提交内容事务，再恢复原 Redis 数据 | 当前提交后失效/索引重建失败没有重试；重点验证旧内容缓存最长约 6 小时、旧发布索引最长约 24 小时的风险窗口 | 新内容可见时间、已下线内容能否继续互动、最终收敛 |
| Redis `noeviction` 内存耗尽 | 隔离环境填充测试 key | 写入明确失败且告警，不能静默丢计数 | 内存水位、失败命令、影响面 |
| Redis 重启/AOF 恢复 | 重启测试实例 | 会话、缓存、计数和 Stream 按持久化窗口恢复 | 数据差异、启动与追平时间 |
| PostgreSQL 延迟/中断 | 网络代理或暂停测试实例 | 热缓存公开读取尽量可用；非缓存接口失败；Stream 积压且不误确认 | 缓存可用率、积压、恢复时间 |
| Consumer 暂停 | 停止调度或测试实例 | Redis 实时值继续，PG 快照滞后，恢复后追平 | 最大 lag 与 drain time |
| 后端重启 | 重启实例 | Redis 会话/缓存保留；Pending 超过 30 秒后可接管 | 停机窗口、错误率、接管时间 |
| CPU/内存/磁盘竞争 | 容器配额或压力工具 | 保护策略生效，无 OOM/数据错乱 | 资源拐点、GC、AOF/PG I/O |
| Redis 与 PG 同时变慢 | 组合注入 | 快速、明确失败，避免线程与连接池级联耗尽 | 故障隔离与恢复顺序 |

每个故障场景均记录五段时间：注入开始、系统检测、用户可见异常、依赖恢复、业务完全恢复。业务完全恢复不仅指接口返回成功，还包括缓存重新变热、Stream 清空、PG 快照追平和关键计数核对一致。

Redis 永久丢失场景需要明确接受边界：系统只能从 PostgreSQL 恢复最近聚合快照，最后一次成功快照之后的实时变化、访客去重状态以及未落库 Stream 消息可能丢失。该结果用于验证备份、AOF 和恢复演练，而不是宣称零数据损失。

## 14. 不同流量压力下的运行策略

以下比例以已验证的 `C_mix` 为基准，并要求相关资源指标同时满足稳定区条件。“当前可执行”只使用现有能力或配置；“候选改造”必须先开发并按本方案复测，不能直接写进运行手册当作已有开关。

| 持续负载 | 当前可执行 | 候选改造（尚未实现） |
|---:|---|---|
| 0～40% | 保持当前配置，正常发布，观察访问日志、Redis 和 Stream 指标 | 补齐统一监控看板和容量趋势预测 |
| 40～60% | 用受控 GET 手工预热三个核心缓存；避免高峰期部署、构建和批量发布 | 发布成功后自动预热 |
| 60～75% | 启动容量告警；核对并按演练结果调整 Nginx/应用静态限流；准备已验证的扩容步骤 | 缓存 TTL 抖动、按接口限流和自动扩缩容 |
| 75～90% | 暂停人工发布等非必要变更；收紧入口流量；仅按连接预算执行已演练扩容 | 业务优先级、后台任务动态暂停和分级降级 |
| >90% 或 SLO 连续失败 | 依靠现有 Nginx 429 保护入口，人工降载；禁止继续放量 | 过载控制器、回源并发舱壁、熔断与明确的快速 503 |

在没有更强故障冗余前，生产长期目标建议不高于 `0.6 × C_mix`，并同时取 Redis 内存稳态容量、PG 连接预算和 Stream 消费容量三者中的最小值。

### 14.1 按瓶颈选择策略

| 观测到的瓶颈 | 状态 | 优先策略 |
|---|---|---|
| 后端 CPU 高，PG/Redis 健康 | 配置/部署 | 增加后端实例前先验证无状态路径、会话共享和 PG 连接预算 |
| Hikari pending 或 PG 连接/CPU 高 | 分析后改造 | 优化慢 SQL和索引、提高缓存命中、限制冷回源；不要盲目增加后端实例 |
| Redis 内存高 | 配置/架构改造 | 测量访客 Hash、负缓存、Stream、每日 key 和缓存占用；扩容或拆分职责，不要只延长 TTL |
| Redis 延迟高或单点风险 | 基础设施改造 | 评估主从 + Sentinel/托管高可用，并考虑会话、缓存、统计的资源隔离 |
| Stream lag 高 | 配置/代码改造 | 优化批处理、PG upsert 和轮询；设计可安全分片的消费者模型，而不是只复制当前单活消费者 |
| 详情冷加载等待高 | 代码改造 | 将共享详情锁细化为按 `postKey` 或分片锁，避免不同详情互相阻塞 |
| 缓存回源接近 1 秒/5 秒 | 配置后复测；部分需开发 | 先依据实测 p99 调整等待和租约；watchdog、TTL 抖动及自动预热需另行实现 |
| 429 高但资源空闲 | 现有配置可调 | 调整 Nginx/应用限流、来源识别和突发额度；这不是算力不足 |
| Redis 故障时请求洪峰冲击 PG | Nginx 已有；其余需改造 | 保留独立入口限流；开发回源并发舱壁、熔断和快速失败 |

扩容后端前必须满足：

```text
后端实例数 × 单实例连接池上限 + 运维/迁移预留连接 < PostgreSQL max_connections
```

当前 PostgreSQL 上限为 30、单实例 Hikari 默认上限为 10，直接扩到 3 个实例就会占满理论连接额度，没有给 Flyway、监控和人工运维留空间。因此扩容必须同时重新设计连接预算，不能只改实例数。

## 15. 中止条件与安全护栏

### 15.1 软中止

连续两个统计窗口违反延迟或资源 SLO 时，停止继续加压，保持当前档短时观察并保存诊断数据。

### 15.2 硬中止

出现以下任一项应立即停止增加流量并进入恢复流程：

- 非预期 5xx 连续 60 秒超过 1%，或连续 10 秒超过 5%；
- 客户端超时超过 1%；
- 公开接口 p99 连续 2 分钟超过 2 秒；
- 后端 CPU 连续 3 分钟超过 90%；
- OOM、容器重启、Full GC 风暴，或单次 GC pause 超过 1 秒；
- GC 后堆占用超过 85% 且不下降；
- Hikari pending 持续 30 秒、连接池耗尽或接近 10 秒获取超时；
- PostgreSQL 连接超过 85%、发生死锁，或磁盘剩余低于 15%；
- Redis 内存超过 90%、出现写拒绝或持续高延迟；
- 最老未落库互动事件超过 60 秒，或最近成功落库距今超过 60 秒；
- Consumer 单批耗时达到 30 秒租约；
- 出现越权、计数错误、版本状态错误、脏写或发布后旧内容复活。

故障演练中符合设计预期的 503 不作为自动中止条件，但一旦超出预先声明的接口、持续时间或错误范围，仍须中止。

| P7 修复与复测 | 缺陷修复、相同脚本回放、阈值校准 | 形成最终容量和运行策略 |

## 18. 最终报告必须回答的问题

1. 当前硬件和配置下，五类容量 `C_warm`、`C_off`、`C_cold`、`C_write`、`C_mix` 分别是多少？
2. 首个瓶颈是 CPU、Tomcat、Hikari、SQL、PG 连接、Redis 延迟/内存，还是限流策略？
3. Redis 对 p95/p99、稳定吞吐、PG 查询和总体资源成本分别改善了多少，置信区间如何？
4. 缓存集中失效、发布后失效及慢回源会把数据库负载放大多少？1 秒等待和 5 秒租约是否合理？
5. Redis、PostgreSQL 或 Consumer 故障时，哪些接口仍可用、哪些数据会旧、哪些写入必须失败，完整恢复需要多久？
6. 在 24～30 小时运行后，匿名访客、Stream 和 AOF 带来的 Redis 内存增长是否可持续？
7. 生产安全流量应设为 `C_mix` 的多少比例，何时告警、扩容、限流、降级和快速失败？
8. 修复关键瓶颈后，用完全相同的脚本复测，收益是否稳定且没有牺牲正确性？

只有这些问题都有数据和证据支撑，才能认为本次系统测试完成。
