# MyBlog 基础系统测试与 Redis 性能对比方案

## 1. 这次测试要解决什么问题

第一次测试不追求一次覆盖所有故障和极限场景，只回答下面四个问题：

1. 登录、内容发布、公开读取、浏览和点赞等主要功能是否正常；
2. 开启公开内容缓存后，接口是否更快、PostgreSQL 压力是否更低；
3. 当前环境在小、中、大三档压力下是否稳定；
4. 流量升高时，应该保持现状、优化数据库、增加后端实例还是进行限流。

完成以下四轮测试并填写结果表，就可以得到第一版系统测试结论：

- 第一轮：核心功能测试；
- 第二轮：Redis 公开内容缓存开关对比；
- 第三轮：简单阶梯压测；
- 第四轮：30 分钟稳定性测试。

## 2. 测试前准备

### 2.1 环境要求

- 只在本地或独立测试环境执行，不要直接压测生产服务器；
- 测试前备份 PostgreSQL 数据；
- 每组对比使用相同代码、相同数据库数据和相同服务器配置；
- 压测期间不要同时构建镜像、运行其他大型程序或修改内容；
- 记录本次 Git 版本、测试日期、电脑或服务器配置。

启动并检查服务：

```powershell
docker compose up -d
docker compose ps
curl.exe http://127.0.0.1:8000/api/v1/health
```

测试工具选择：

- 浏览器或 Postman：执行功能测试；
- k6 或 JMeter：执行简单压测，选择自己更熟悉的一个即可；
- `docker stats`：观察后端、PostgreSQL 和 Redis 的 CPU、内存。

```powershell
docker stats
```

### 2.2 先处理限流影响

项目当前有两层限流：Nginx 普通 API 约 10 次/秒/IP，应用普通接口默认 60 次/分钟/IP。如果直接用一台压测机持续发请求，很快会得到 429；这只能证明限流生效，不能代表系统性能上限。

基础容量测试应在隔离环境使用测试专用配置提高限流阈值，并保持两组配置完全相同。当前后端只绑定宿主机 `127.0.0.1:8000`，最简单的方式是在被测主机上执行 k6/JMeter，或者通过 SSH 隧道访问。不要为了压测把后端端口开放到公网。

如果暂时不会调整测试限流，可以先完成核心功能和低并发对比；一旦出现 429，就停止提升压力，并把结果标记为“达到限流阈值”，不要标记为“达到系统容量”。

## 3. 第一轮：核心功能测试

先手工执行下面的主流程。每一项只记录“通过、失败、实际现象”即可。

### 3.1 健康检查

| 操作 | 预期结果 |
|---|---|
| 访问 `/api/v1/health` | 接口成功，数据库和 Redis 均为 up |
| 查看 `docker compose ps` | 所有主要容器处于运行或 healthy 状态 |
| 查看后端日志 | 没有持续重复的数据库、Redis 或内存错误 |

### 3.2 登录和会话

| 操作 | 预期结果 |
|---|---|
| 使用正确账号登录 | 登录成功，能够访问后台 |
| 使用错误密码登录 | 返回明确错误，不能进入后台 |
| 登录后刷新页面 | 会话仍有效 |
| 退出登录 | 当前 Token 立即失效 |
| 修改密码后使用旧 Token | 旧会话失效，需要重新登录 |

登录有 BCrypt 计算和独立限流，本轮只验证功能，不对登录接口做高并发压测。

### 3.3 内容版本管理

选择一个测试模块，依次执行：

1. 创建或保存草稿；
2. 再次编辑草稿；
3. 发布草稿；
4. 在博客前台查看新内容；
5. 查看历史版本；
6. 恢复一个历史版本；
7. 下线内容。

主要检查：

- 发布前，草稿不会出现在公开页面；
- 发布后，公开页面能看到新内容；
- 历史版本内容没有被后续编辑修改；
- 恢复版本后，草稿内容正确；
- 下线后，公开接口不再返回该内容；
- 任一步骤失败时，不应出现一半成功、一半失败的数据。

### 3.4 公开内容

测试以下三个主要读取接口：

- `GET /api/v1/public/content`
- `GET /api/v1/public/content/mylab`
- `GET /api/v1/public/mylab/{postKey}`

检查首页、MyLab 列表和详情的字段、排序、图片、Markdown 正文和标签是否正确。不存在或未发布的 `postKey` 应返回 404，而不是服务器错误。

### 3.5 浏览和点赞

| 操作 | 预期结果 |
|---|---|
| 新浏览器首次访问 | UV/PV 按项目口径增加 |
| 同一浏览器重复刷新 | 24 小时窗口内不重复增加同一页面浏览 |
| 首次点赞 | 点赞数增加 1 |
| 重复点赞 | 点赞数不重复增加 |
| 取消点赞 | 点赞数减少 1，且不会变成负数 |
| 等待数秒后查看后台统计 | PostgreSQL 快照最终与前台计数一致 |

使用浏览器隐私窗口可以模拟新的匿名访客。生产环境 Cookie 带 `Secure`，压测互动接口时应使用 HTTPS；直连 HTTP 可能无法正确保存访客 Cookie，导致结果失真。

## 4. 第二轮：Redis 公开内容缓存对比

### 4.1 对比范围

只比较三个公开内容读取接口。不要通过停止 Redis 来模拟“没有 Redis”，因为登录、互动统计和限流也依赖 Redis，停机后业务语义会改变。

正确的两组配置是：

| 组别 | 配置 | 含义 |
|---|---|---|
| A：关闭内容缓存 | `CONTENT_CACHE_ENABLED=false` | 公开内容直接查询 PostgreSQL，但 Redis 仍正常运行 |
| B：开启内容缓存 | `CONTENT_CACHE_ENABLED=true` | 公开内容优先从 Redis 读取 |

每次切换配置后都要重启后端，并确认健康检查通过后再开始测试。

### 4.2 简单测试步骤

对 A、B 两组分别执行完全相同的步骤：

1. 使用同一份数据库数据启动系统；
2. 启动后先访问接口 10 次，让 JVM 和数据库完成基本预热；
3. 使用 5 个并发用户运行 3 分钟；
4. 使用 10 个并发用户运行 5 分钟；
5. 如果没有 429、超时或明显错误，再使用 20 个并发用户运行 5 分钟；
6. 记录 p95 响应时间、每秒完成请求数、错误率，以及三个容器的 CPU、内存；
7. 每组至少执行两次，结果差异很大时再执行第三次。

B 组测试前只清理公开内容缓存，不要执行 `FLUSHDB`，否则会同时删除会话、互动统计和限流数据。当前相关 key 为：

```text
mylab:blog:content:v3:all
mylab:blog:content:v2:mylab:summary
mylab:blog:content:v1:mylab:details
```

清理后第一次请求属于冷缓存，应单独记录；随后再访问数次完成预热，正式记录热缓存结果。

### 4.3 需要记录的指标

| 指标 | 为什么要看 |
|---|---|
| p95 响应时间 | 表示 95% 的请求都能在这个时间内完成 |
| 完成 RPS | 表示系统每秒真正完成多少请求 |
| 错误率 | 查看是否出现 429、500、503 或超时 |
| 后端 CPU/内存 | 判断应用本身是否成为瓶颈 |
| PostgreSQL CPU/内存 | 判断 Redis 是否降低数据库压力 |
| Redis CPU/内存 | 判断获得缓存收益付出了多少 Redis 成本 |

计算两个最容易理解的结果：

```text
响应时间改善率 = (关闭缓存 p95 - 开启缓存 p95) / 关闭缓存 p95 × 100%
吞吐提升率     = (开启缓存 RPS - 关闭缓存 RPS) / 关闭缓存 RPS × 100%
```

如果开启缓存后 p95 下降、完成 RPS 上升、PostgreSQL CPU 下降，而且接口返回内容一致，就可以认为 Redis 带来了有效收益。

## 5. 第三轮：简单阶梯压测

第一次容量测试建议先以公开读取为主，不要把登录、发布和文件上传混在一起。

推荐流量比例：

| 请求 | 比例 |
|---|---:|
| 首页聚合 | 40% |
| MyLab 列表 | 30% |
| MyLab 详情 | 30% |

按下面顺序逐步增加压力：

| 阶段 | 并发用户 | 持续时间 | 目的 |
|---|---:|---:|---|
| 冒烟 | 1 | 1 分钟 | 确认脚本和接口正确 |
| 低压力 | 5 | 3 分钟 | 建立正常基线 |
| 中压力 | 10 | 5 分钟 | 观察响应时间和数据库压力 |
| 较高压力 | 20 | 5 分钟 | 找出是否开始变慢 |
| 可选加压 | 30、40、50 | 每档 5 分钟 | 只在上一档稳定时继续 |

每一档结束后休息 1～2 分钟，确认 CPU、连接和响应时间恢复，再进入下一档。

出现以下任一情况就停止继续加压：

- 非预期错误率超过 1%；
- p95 连续超过 2 秒；
- 后端或 PostgreSQL CPU 持续超过 85%；
- 容器重启或内存持续增长；
- 出现数据错误、点赞负数或发布内容不一致；
- 出现大量 429。大量 429 表示先碰到了限流，而不是系统算力上限。

把“满足错误率、响应时间和资源要求的最高一档”记录为当前环境的初步安全压力。它只是当前测试机器的参考值，不等于生产容量。

## 6. 第四轮：基础稳定性测试

选择上一轮最高稳定并发的 50%～60%，持续运行 30 分钟。

期间执行一次内容发布，并检查：

- 发布接口正常成功；
- 新内容能及时出现在首页、列表和详情；
- 没有旧内容重新覆盖新内容；
- p95 没有长期升高；
- 后端、PostgreSQL 和 Redis 内存没有持续上涨；
- 停止压测后 1～2 分钟内，CPU 和响应时间回到正常水平。

第一次测试做到这里就足够。完成上述结果后，再考虑 Redis 重启、PostgreSQL 故障、长时间压测等高级场景。

如果希望做一个最简单的 Redis 故障检查，可以只在低压力下短暂停止 Redis：公开内容读取应尝试回源 PostgreSQL，而登录和互动写入可能返回 503。恢复 Redis 后确认接口恢复即可。不要在第一次测试中同时注入多个故障。

## 7. 如何根据结果选择策略

| 测试现象 | 判断 | 建议动作 |
|---|---|---|
| p95 较低、错误为 0、CPU < 60% | 系统余量充足 | 保持当前配置，继续监控 |
| 开启缓存明显更快，PG CPU 明显下降 | Redis 缓存有效 | 保持缓存开启，在发布后手工访问核心接口完成预热 |
| 关闭缓存后 PG CPU 很快升高 | 数据库是主要瓶颈 | 优先保持缓存命中、检查 SQL 和索引，不要先增加后端实例 |
| 后端 CPU 高，但 PG/Redis 较低 | 应用计算是瓶颈 | 再考虑增加后端实例，并重新测试 |
| Redis 内存不断升高 | Redis 容量存在风险 | 检查访客、Stream 和负缓存数据量，再决定扩容或调整保留时间 |
| p95 超过 1 秒或错误率开始增加 | 接近系统上限 | 降低入口流量，避免高峰发布，定位最先升高的 CPU/内存 |
| 大量 429，但资源仍很空闲 | 碰到限流规则 | 单独调整测试限流；不要误判为性能不足 |
| Redis 故障后 PG CPU 激增 | 回源能力有限 | 保留 Nginx 限流，Redis 故障时主动降低流量，保护数据库 |

后端扩容前要注意：当前每个实例的数据库连接池默认约 10，PostgreSQL 最大连接数为 30。不能直接增加很多后端实例，否则数据库连接会先耗尽。

## 8. 基础验收标准

第一轮可以使用以下简单标准：

- 所有核心功能测试通过；
- 公开内容开启和关闭缓存时返回结果一致；
- 正常压力下非预期错误率低于 1%；
- 期望流量下公开读取 p95 低于 500 ms；
- 后端、PostgreSQL 和 Redis CPU 不持续超过 80%；
- 没有容器重启、OOM、数据错乱和计数负数；
- 开启缓存后，响应时间或吞吐至少有一项改善，同时 PostgreSQL 压力下降；
- 30 分钟稳定性测试中，延迟和内存没有持续恶化。

这些是第一次摸底用的参考标准。测试完成后，应根据真实结果调整，而不是为了通过测试去隐藏错误或放宽数据正确性要求。

### 9.3 最终结论

只需要回答下面五个问题：

1. 核心功能是否全部正常？
2. 开启 Redis 内容缓存后，p95 和 RPS 分别改善多少？
3. Redis 是否明显降低 PostgreSQL CPU 或查询压力？
4. 当前测试环境能稳定通过的最高并发档位是多少？
5. 首先出现的瓶颈是限流、后端、PostgreSQL 还是 Redis？

能用测试数据回答这五个问题，就完成了第一版基础系统测试。
