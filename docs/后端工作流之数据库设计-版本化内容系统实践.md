# 后端工作流之数据库表设计

数据库表设计的目标，是把业务概念转换为结构清晰、约束明确、便于演进的数据模型。设计时不应直接从字段开始，而应按照需求、实体、关系、约束和验证逐步推进。

## 一、明确设计范围

开始设计前，先确认：

- 哪些数据需要持久化；
- 哪些数据只是临时状态或计算结果；
- 是否需要历史记录、软删除和审计；
- 数据量、访问频率和一致性要求；
- 本期明确不处理的功能。

范围不清会导致表结构不断临时扩展，最终产生重复字段和职责重叠的表。

## 二、识别实体

从业务名词中提取实体，例如用户、订单、文章、文件等。判断一个概念是否应该独立成表，可以考虑：

- 是否拥有独立生命周期；
- 是否会被多个对象引用；
- 是否需要单独查询、修改或删除；
- 是否包含多个有业务意义的属性。

仅用于展示、没有独立生命周期的数据，通常不需要单独建表。

## 三、确定实体关系

使用 ER 图确认实体之间的关系：

- 一对一；
- 一对多；
- 多对多。

常见实现方式：

| 关系 | 实现方式 |
| --- | --- |
| 一对一 | 外键加唯一约束 |
| 一对多 | 多的一方保存外键 |
| 多对多 | 建立中间关联表 |

关联表除了保存两个外键，还可以保存排序、状态、创建时间等关系属性。

## 四、设计字段

字段设计应遵循以下原则：

- 名称准确表达业务含义；
- 类型与真实数据范围匹配；
- 明确字段是否允许为空；
- 布尔值、状态值和时间字段保持统一风格；
- 避免把多个含义存入同一个字段；
- 避免保存可以稳定计算得到的重复数据。

常见通用字段：

```text
id
created_at
updated_at
deleted_at
```

主键可以使用自增整数或 UUID，应根据系统规模、分布式需求和数据暴露方式统一选择。

## 五、定义数据约束

数据库约束是数据完整性的最后防线。

优先使用：

- `NOT NULL`：必填字段；
- `PRIMARY KEY`：唯一标识；
- `FOREIGN KEY`：引用完整性；
- `UNIQUE`：业务唯一性；
- `CHECK`：状态、范围和字段组合；
- 默认值：统一初始状态。

可以由数据库直接表达的规则，不应只依赖前端或后端校验。

涉及跨表查询、操作阶段或复杂业务流程的规则，更适合由后端服务校验。

## 六、选择删除策略

常见删除方式：

- 物理删除：数据直接移除；
- 软删除：通过 `deleted_at` 或状态字段标记；
- 限制删除：存在引用时拒绝；
- 级联删除：父数据删除时同时删除子数据；
- 外键置空：删除被引用对象后保留业务记录。

选择删除策略时，需要考虑：

- 数据是否需要审计和恢复；
- 子数据是否能独立存在；
- 历史记录是否仍需要展示；
- 删除是否涉及文件或其他外部资源。

级联删除应谨慎使用，避免一次操作意外删除大量数据。

## 七、设计索引

索引应根据实际查询方式设计，而不是为所有字段都建立索引。

优先考虑：

- 主键和唯一键；
- 外键字段；
- 高频查询条件；
- 排序和分页字段；
- 多字段组合查询。

联合索引的字段顺序应与常见查询条件匹配。索引会增加写入和存储成本，需要避免重复或长期不用的索引。

## 八、划分数据库与后端职责

适合数据库保证的规则：

- 主键、外键和唯一性；
- 非空和默认值；
- 数值范围；
- 固定状态取值；
- 简单字段组合关系。

适合后端服务处理的规则：

- 跨表业务校验；
- 权限判断；
- 状态流转；
- 多步骤事务；
- 外部文件和第三方服务操作；
- 与操作场景有关的动态规则。

触发器只适合少量必须对所有写入方式生效、且无法用普通约束表达的稳定规则，不应承载复杂业务流程。

## 九、设计事务边界

一个业务操作涉及多张表时，应明确事务范围。例如创建主记录、明细和关联数据，应在同一事务内完成。

事务设计需要考虑：

- 哪些操作必须全部成功或全部失败；
- 是否存在并发修改；
- 是否需要乐观锁或悲观锁；
- 锁的范围是否过大；
- 外部服务失败如何补偿。

数据库事务不应长时间等待网络请求。文件上传、消息发送等外部操作应设计重试或补偿机制。

## 十、编写迁移脚本

表结构应通过 Flyway、Liquibase 等迁移工具管理，而不是手工修改环境数据库。

迁移脚本应具备：

- 可重复部署到不同环境；
- 执行顺序明确；
- 已执行脚本不随意修改；
- 新旧版本之间具备数据迁移方案；
- 可以在空数据库中完成初始化。

生产环境已经执行过的迁移，应通过新增迁移文件继续演进。

## 十一、进行设计验收

设计完成后至少检查：

- 表职责是否单一；
- 是否存在重复数据源；
- 实体关系是否正确；
- 外键和删除策略是否合理；
- 业务唯一性是否有约束；
- 空值和默认值是否符合业务语义；
- 索引是否覆盖主要查询；
- 并发和事务边界是否明确；
- 迁移脚本能否从空库执行；
- 后端接口是否遵循表结构和数据生命周期。

## 十二、总结

数据库表设计可以归纳为：

```text
明确范围
  → 识别实体
  → 确定关系
  → 设计字段
  → 定义约束
  → 规划删除和索引
  → 划分职责
  → 设计事务
  → 编写迁移
  → 验证结果
```

好的表设计不追求复杂，而是让数据含义明确、规则能够执行、结构容易维护，并为后续业务变化保留清晰的演进路径。
