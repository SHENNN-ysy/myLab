# 代码改动说明编写规则书

> 本规则书规定项目内「代码改动开发说明」文档的统一结构、写法与质量要求。
> 所有涉及架构调整、认证改造、存储变更、接口契约修改等具有一定规模的代码改动，完成后都应产出一份符合本规则的 `.md` 说明文档，存放于 `docs/` 或 `article/` 目录。
> 编写时可对照参考样例：[Redis会话令牌认证改造开发说明](./Redis会话令牌认证改造开发说明.md)。

## 1. 总则

### 1.1 文档定位

改动说明面向**未来的维护者**（包括几个月后的自己），回答四个问题：

1. **为什么改** —— 动机、解决的问题、消除的复杂性。
2. **改了什么** —— 范围边界、关键设计、数据结构与流程。
3. **怎么改的** —— 逐文件、逐层级的代码改动清单及其带来的功能变化。
4. **怎么验证与发布** —— 测试证据、上线影响、回滚预案、验收清单。

### 1.2 写作原则

1. **陈述事实，不写过程**：写「改成了什么」和「为什么这样改」，不写开发过程中的试错、犹豫或聊天式叙述。
2. **边界先行**：明确「改造范围」与「不受影响的范围」，让读者一眼判断自己的模块是否受影响。
3. **代码改动为主体，功能变化为落点**：每条代码改动都要落到「它使系统行为发生了什么变化」上，不做无行为含义的罗列。
4. **每个设计决策必须带理由**：例如「不缓存用户名、角色或启用状态」必须紧跟「避免角色变更或账号停用后继续使用旧权限」。没有理由的规则无法被后人判断何时可以打破。
5. **显式声明「没做什么」**：容易被误认为做了的事（如「没有新增数据库字段」）要专门点明，防止读者按旧认知做推断。
6. **证据可复现**：测试结果、检查结果必须附执行命令与可重跑的验证步骤，禁止只写「测试通过」。
7. **语言**：中文书写，使用规范技术术语；专有名词、配置项、类名、路径保持原文，不翻译。

## 2. 文档结构（必备章节）

章节按以下顺序组织。小改动可合并或删减，但第 1、3、6 章不可省略。

```text
# <改动主题>开发说明
1. 改造目标与范围
2. 核心数据结构 / 关键设计
3. 代码改动
4. 异常处理与故障语义
5. 测试代码位置
6. 测试结果
7. 上线与回滚
8. 上线检查（验收清单）
```

### 2.1 改造目标与范围

- **第一段**：用 2~4 句话概括改动：把什么替换成什么 / 新增了什么，解决了什么问题，带来了什么新能力。
- **改造范围**：无序列表，逐条列出受影响的端（前台/后台/后端/部署/文档）。
- **不受影响的范围**：无序列表，明确排除项，至少覆盖：公开接口、其他端的流程、数据库结构是否变更、客户端存储契约是否变更。
- **关键否定声明**：本节末尾用一段话说明本次改动「刻意没有做」的事及其替代方案，例如：

  > 本次改造没有为 `users` 增加 `auth_version`，也没有新增任何数据库字段或表。登录与敏感账号写操作的并发一致性由 PostgreSQL 用户行锁保证。

### 2.2 核心数据结构 / 关键设计

- 涉及 Redis、数据库、消息队列等存储结构变更时，**必须用表格**描述每个 Key / 表 / 主题：

  | Redis Key | 类型 | 内容 | TTL |
  |---|---|---|---|
  | `auth:session:{token_sha256}` | Hash | `user_id`、`created_at`、`last_seen_at` | 空闲 8 小时，认证成功后续期 |

- 涉及客户端可见的凭证或数据格式时，给出**实际样例**（代码块），并说明安全语义，例如「Redis Key 只保存摘要，即使被读取也不能还原客户端凭证」。
- 每个字段级的取舍都要给出理由（见 1.2 第 4 条）。

### 2.3 代码改动

本章是文档的主体，**以代码改动清单为骨架，逐项说明改动内容及其带来的功能变化**。流程、机制、并发语义的变化不再单独成章，而是跟随对应的代码改动一并说明——读者看到某个文件、某个方法改了什么，同时就能看到系统行为因此变成了什么样。

**（1）组织方式**

- 按**架构分层 / 端 / 模块**分小节（如「Application Port」「Redis Adapter」「管理后台」「配置与部署」），不是按提交顺序。
- **每个改动文件一个四级标题，标题写完整仓库相对路径**，路径用反引号包裹：

  ````markdown
  #### `backend-java/src/main/java/com/myblog/application/port/SessionService.java`
  ````

**（2）条目写法：动作动词 + 对象 + 作用 / 变化说明**

- 每个文件下用短横线列表描述改动，每条一个关注点。**每条必须以明确的动作动词开头，并写清改动对象与改动带来的作用或功能变化**。
- **动作动词必须从以下集合中选择**，不允许使用「更新」「调整」「处理」等模糊动词：

  | 动作动词 | 适用场景 | 示例 |
  |---|---|---|
  | 新增 | 新文件、新方法、新字段、新配置项、新接口 | 新增 `issue()` 方法，生成随机 UUID Token 并以 Lua 脚本原子写入会话 Hash 与用户 ZSet。 |
  | 删除 | 移除类、方法、接口、依赖、配置项 | 删除 `/auth/refresh` 接口及其 DTO，客户端不再存在刷新令牌入口。 |
  | 修改 | 已有方法 / 逻辑 / 配置的行为变化 | 修改 `login()` 方法，改为先锁定用户行再校验凭证，登录与账号修改之间不再存在并发窗口。 |
  | 替换 | 一个实现整体换成另一个实现 | 使用 `SessionAuthenticationFilter` 替换原 `JwtFilter`，认证来源从 JWT 解析改为 Redis 会话读取。 |
  | 移动 / 重命名 | 仅位置或名称变化、行为不变 | 重命名 `TokenPairVO` 为 `AccessTokenVO`，仅保留 access token 相关字段。 |

- 条目的信息含量要求：
  - **新增 / 替换**：必须说明新增对象的作用（解决什么问题、被谁调用）。
  - **修改**：必须对比说明「改之前 → 改之后」的行为差异，以及差异带来的效果。
  - **删除**：必须说明删除对象原先的用途，以及删除后由什么替代或为何不再需要。
  - **移动 / 重命名**：必须注明行为是否变化；无变化时写明「行为不变」。

  正例（每条有动作、有对象、有作用）：

  - 新增 `findByUsernameForUpdate(username)` 仓储方法，登录时按用户名锁定用户行，与账号修改操作互斥。
  - 修改 `logout` 接口，不再接收请求体，直接注销 Authorization 请求头中的当前会话，不影响同一用户在其他设备上的登录。
  - 删除 `JwtService`、`JwtUtil` 和 `JwtFilter`，JWT 签发与解析能力由 Redis 会话服务整体接管。
  - 新增 `app.session.idle-timeout` 配置绑定，校验空闲超时必须大于 0，并转换为 Redis `EXPIRE` 使用的秒数。

  反例（禁止出现）：

  - ~~更新了 `AuthServiceImpl.java`~~（无动作、无内容）
  - ~~优化了登录逻辑~~（无对象、无变化说明）
  - ~~处理了会话相关问题~~（无动作、无对象、无作用）

- **删除的类型 / 依赖 / 接口必须显式列出**，与新增同等重要（如「删除 `JwtService`、`JwtUtil` 和 `JwtFilter`」「从 Maven 依赖中删除 JJWT」）。
- 配置文件改动要给出**变更后的配置示例**（`.env` / `yml` 代码块），并说明占位符、默认值与回滚兼容策略。
- 涉及密钥 / 凭据的配置，必须提醒「两个密钥必须使用不同的随机值」之类的安全约束。

**（3）功能变化的展开要求**

代码改动引起流程、机制或并发语义变化时，必须在对应小节内（条目之后或重要改动单独设段）把变化后的行为讲清楚，不能只停留在条目级别：

- **流程变化**：用**有序编号列表**描述变化后的步骤，一步一句，动词开头，并标注锁、事务、原子操作的边界（「在锁内」「Lua 脚本原子执行」「事务提交后」），例如：

  1. 根据用户名执行 `SELECT ... FOR UPDATE`，锁定目标用户行。
  2. 在锁内重新检查用户是否存在、是否启用以及密码是否匹配。

- **接口契约变化**：给出**变更后的 JSON 响应示例**，并注明哪些字段保留、哪些删除（如「保留原有 `tokens` 外层结构，仅删除 `refresh_token`」）。
- **机制行为**：说明改动后机制的幂等性、清理策略、边界情况（如「会话已经不存在时保持幂等」），并列出触发该机制的全部调用点（如「以下操作成功时会调用 `revokeAll`：……」）。
- **容易误解的语义必须专门澄清**，例如：

  > 滑动 TTL 表示 `expires_in=28800` 是空闲超时时间，不是从首次登录开始计算的固定绝对有效期。

- **并发与事务语义**：改动涉及并发或跨系统写入时，必须说明：
  1. 使用的同步原语（行锁、乐观锁、Lua 原子脚本等）及其粒度；
  2. **竞态分析**：两个并发操作的每种先后顺序分别产生什么结果，用编号列表穷举；
  3. **跨系统一致性边界**：数据库与 Redis / MQ 等无法组成单一 ACID 事务时，声明采用的故障语义（安全优先 / 可用优先），并用列表给出每种失败场景的最终状态，例如：

     - 登录创建会话失败：抛出 503，登录事务回滚。
     - Redis 吊销成功但数据库提交失败：会话可能被提前踢出，但账号数据不会产生权限安全不一致。

- 有旁路 / 白名单逻辑变化时，用列表穷尽豁免路径，并说明旁路带来的故障隔离效果。

### 2.4 异常处理与故障语义

- 新引入的错误码用表格列出（code / HTTP / 枚举 / 含义）。
- 说明**客户端对各错误码的行为差异**：哪些错误码清理本地状态并跳转登录，哪些保留状态等待恢复，必须区分清楚（如 401 vs 503 的处理差异）。
- 遗留 / 废弃的错误码要说明保留原因（避免编号歧义）和废弃标记。

### 2.5 测试代码位置

- 按测试类逐节列出，标题写测试文件的仓库相对路径。
- 每个测试类下用列表说明**验证了哪些行为**，写行为不写方法名，例如：

  - 验证登录响应只包含 UUID access token，不包含 refresh token。
  - 验证 Redis 故障返回 HTTP 503 和 code `10014`，不会被转换为 401。

- 删除的测试也要显式列出并说明原因。
- 本节是「什么行为被测试保护了」的索引，供后续改动评估回归风险。

### 2.6 测试结果

- 每个端 / 每个质量门一个子节，**先给执行命令，再给实际结果**：

  ````markdown
  执行：

  ```bash
  cd backend-java
  mvn verify
  ```

  实际结果：

  - 单元测试：270 个，全部通过。
  - Checkstyle：通过。
  - SpotBugs：0 个问题。
  - Maven：`BUILD SUCCESS`。
  ````

- 数字必须如实填写（测试数、问题数）；存在的既有警告 / 提示要如实说明并注明与本次改动无关。
- 禁止只写「测试全部通过」而不给命令与明细。

### 2.7 上线与回滚

- **发布顺序 / 版本绑定**：多端联动改动必须说明是否必须同版本发布，以及只更新一侧的后果。
- **上线影响**：列出对用户 / 存量数据 / 存量凭证的影响（如「所有后台用户上线后需要重新登录一次」）。
- **回滚观察期**：保留的旧配置、新旧版本互不识别的情况、回滚后的用户影响、观察期结束后的清理动作。

### 2.8 上线检查（验收清单）

- 按维度分小节（如「API 验收」「Redis 检查」「故障语义检查」）。
- 每条是可操作的验证动作 + 预期结果，编号列表，例如：

  1. 登录后确认响应只有 `access_token`、`token_type` 和 `expires_in`，没有 `refresh_token`。

- 涉及中间件状态的检查，给出**可直接复制执行的命令**，例如：

  ```bash
  docker compose exec redis redis-cli HGETALL auth:session:<token_sha256>
  ```

- 安全相关的负向检查也要列出（如「Redis 中不应出现客户端 UUID 原文、密码、用户名或角色」）。
- 故障语义检查要覆盖所有组合：正常 + 无效凭证、故障 + 有效凭证、旁路接口、跨系统部分失败。

## 3. 格式规范

| 项 | 规则 |
|---|---|
| 文件格式 | Markdown（`.md`），UTF-8 编码 |
| 一级标题 | 仅一个，`# <主题>开发说明` |
| 章节编号 | 二级标题从 `## 1.` 顺序编号；三级 `### 1.1`；四级标题（文件条目）不编号 |
| 文件路径 | 始终写仓库根目录相对路径，反引号包裹，如 `admin/src/utils/request.ts` |
| 代码元素 | 类名、方法名、配置项、Redis Key、接口路径一律用行内代码（反引号） |
| 代码块 | 注明语言（`json` / `bash` / `env` / `text` / `http`） |
| 表格 | 数据结构、错误码、对比信息优先用表格 |
| 敏感信息 | 文档中的密钥、密码一律使用占位示例值（如 `change-this-xxx`），禁止出现真实凭据 |
| 图表 | 复杂流程可补 ASCII 流程图或 Mermaid，但不能替代编号步骤列表 |

## 4. 写作清单（提交前自查）

- [ ] 第 1 章：一句话能说清「把什么改成了什么」；范围与不受影响范围都有列表。
- [ ] 第 1 章：明确声明了「没做什么」（表结构、契约、存储方式等）。
- [ ] 所有设计决策都附了理由，读者能判断规则何时可以打破。
- [ ] 数据结构有表格；接口契约变化有 JSON 示例；配置变化有配置示例。
- [ ] 代码改动章按层分节、每文件一个标题、路径完整。
- [ ] 改动清单每条都以「新增 / 删除 / 修改 / 替换 / 移动 / 重命名」开头，并写明对象与作用 / 变化；删除项与新增项并列。
- [ ] 改动引起的流程变化有编号步骤并标注锁 / 事务 / 原子操作边界；机制变化写清了幂等性、清理策略、边界情况与全部调用点。
- [ ] 并发竞态穷举了先后顺序的各种结果；跨系统故障语义逐场景说明。
- [ ] 错误码表格完整；客户端对不同错误码的行为差异写清楚了。
- [ ] 测试章节：测试类路径 + 行为列表；删除的测试也说明了。
- [ ] 测试结果：每个质量门都有执行命令 + 如实数字，既有警告已注明与本次无关。
- [ ] 上线与回滚：版本绑定、用户影响、观察期保留项与清理动作齐全。
- [ ] 上线检查：每条可操作、有预期结果；中间件检查命令可直接复制执行。
- [ ] 全文无真实密钥、无聊天式叙述、无「测试通过」式无证据断言。
- [ ] 改动涉及的结构 / 命令 / 约定如与 `AGENTS.md` 冲突，已同步更新 `AGENTS.md`。
